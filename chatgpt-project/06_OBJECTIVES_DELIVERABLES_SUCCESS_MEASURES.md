# Objectives, Deliverables, and Success Measures

Keep these categories separate.

## Business outcome

The business condition the project supports. Example: reduce customer onboarding cycle time.

## Project objective

The project-level result the team is expected to achieve. Example: deploy a standardized onboarding control workflow across three regions.

## Deliverable

The authorized output. Example: intake form, dashboard, standard operating procedure, training package, integration release.

## Success measure

The measure used to judge whether the work achieved the intended result. Example: reduce average onboarding cycle time from 18 days to 10 days by Q4.

## Value gate for regular initiatives

For non-AI initiatives, classify value without forcing fake precision:

- Hard financial
- Cost avoidance
- Revenue protection
- Mission value
- Risk reduction
- Quality/rework
- Cycle time
- Customer/employee experience
- Compliance/control
- Strategic option value

For each material claim, name baseline availability, assumptions, confidence,
finance-validation status, and cost of doing nothing. Only hard financial
benefits with validated method and owner should be treated as ROI. A charter may
authorize delivery while value measurement remains provisional.

When a success measure represents a value claim, carry it as a measurement contract:

- Expected outcome.
- Benefit type.
- Metric.
- Baseline.
- Target.
- Actual, if available.
- Measurement period.
- Source.
- Measure owner.
- Review cadence.
- Validation need.
- Confidence.
- Realization risk.
- Finance-sensitive flag.
- Downstream route.

If the charter authorizes delivery but the value measure is not ready, mark the missing fields instead of inventing them. Do not treat acceptance of a deliverable as proof that the benefit was realized.

## Acceptance condition

The evidence required to close the project. Example: sponsor signs off that dashboard, process, training, and handoff are complete.
